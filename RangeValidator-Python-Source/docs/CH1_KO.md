# C/H-1 구조체·typedef·변수 매칭 진단

## 작업 범위와 호출 경로

실제 Git 루트는 `C:\Range`, 브랜치는 `main`, 시작 커밋은 `c93f379`이었다. 기존 Clang-1 작업 트리와 Excel-6 기준선 산출물을 유지했다. 기준선 재빌드 EXE의 SHA-256은 앞서 기록한 `EF3BA7271200CD99393892FFB00796E01E861256232560DCE49574AF42839DFB`와 일치했다.

1. `workflow._run_comparison()`이 전달된 C/H를 `engine.catalog_headers()`에 보낸다. `bitfield_catalog.build_bitfield_catalog()`가 파일 읽기와 인코딩 대체를 수행하고 `_collect()`가 주석 제거, include guard 인식, 조건부 선언 표시, 인용형 상대 include 연결, 토큰화 및 선언 수집을 담당한다.
2. `_Collector`는 `analysis._Parser`를 사용해 구조체 본문과 멤버를 읽고 비트폭 표현식을 보관한다. 별도 typedef, 함수 원형, 정의, 지역 선언을 별도로 수집한다. `_Registry.resolve()`는 파일 가시성과 선언 위치를 기준으로 typedef와 태그를 원본 정의에 연결한다. `_field()`는 폭·부호·범위를 계산하고 `_bind_variables()`, `_bind_functions()`가 전역 및 함수 문맥을 연결한다.
3. `catalog_headers()`는 별도의 `analysis.analyze()` 결과도 병합해 레거시 카탈로그를 만든다. 현재 Excel 매칭이 사용하는 구조체 증거는 `catalog.bitfields`다.
4. Workbook을 읽은 뒤 `engine.compare_book()`이 `scan_a()`와 `scan_b()`로 헤더와 같은 행의 셀을 확인한다. 상세설계서 이름에서 C 파일 힌트를, 시트 이름에서 함수명을 얻는다. `MEMBER_ACCESS` 및 비트필드 이름 인덱스 검사를 통과한 행만 `_catalog_match()`로 간다. 그다음 선언·포인터/배열 형태·비트필드 범위를 검사한다. `TYPE_MATCH` 뒤 범위 셀의 수식·병합·공란·내용을 확인해 기존 결과를 만든다.

`rangevalidator/ch_diagnostics.py`의 `CHDiagnostics`는 이 카탈로그와 수집 단계의 관찰을 함께 보고한다. `trace_expression()`은 행이 빠진 지점과 후보 선언을 기록하고, `workbook()`은 기존 `compare_book()` 결과에 `diagnose_workbook()`의 셀 증거를 붙인다. 진단 전후의 production 결과와 커버리지 일치를 테스트했다. 이 모듈을 호출하는 GUI·업무 파이프라인·Writer 경로는 없다. JSON은 명시적으로 실행한 합성 도구에만 저장되며 경로와 코드 이름을 포함한다.

## 합성 A/B Workbook

C/H 5개에서 구조체 정의 11개, typedef 선언 12개, 비트필드 15개를 발견했다. 변수 인벤토리는 전역 22개, 지역 3개, 정의의 매개변수 1개였다. 그중 구조체 타입 연결 성공 19개, 미확정 7개였다. 이 숫자에는 파서가 전혀 수집하지 않은 선언이 들어가지 않는다. 독립 정답으로 확인한 유효 선언의 조용한 누락은 빈 `cinst` 사례 1건이다.

실제 OpenPyXL Reader로 읽은 A/B 시트의 진단 표현식은 34개였다. C/H 범위 확인 15개 중 14개가 MATCH였고 1개는 Excel의 수식 때문에 REVIEW였다. 기존 결과 총계는 MATCH 14개, REVIEW 14개, 결과 미생성 6개다. 실제 Excel COM Reader로 같은 합성 Workbook을 읽기 전용으로 검증했고, 34개 행의 시트·표현식·셀 주소·판정·진단 코드가 OpenPyXL 결과와 일치했다. [COM Reader 검증 결과](../build/ch1-com-reader.json)

| 기존 REVIEW의 상세 원인 | 건수 |
|---|---:|
| 구조체 정의 없음 | 2 |
| typedef 미해결 | 1 |
| 변수 선언 미발견 | 2 |
| 변수 타입 미해결 | 1 |
| 포인터 타입 또는 접근 형태 미해결 | 2 |
| 배열 요소 타입 또는 접근 형태 미해결 | 2 |
| 전처리 조건 미확정 | 2 |
| 비트폭 매크로 미확정 | 1 |
| C/H 범위 확인 후 Excel 수식으로 REVIEW | 1 |

- `can_data1.state`, `can_data_p->state`, `can_data_array[0].state`는 모두 `0~7`이다. `static` 변수의 `active`는 `0~1`이다. 잘못된 점/화살표와 배열 첨자 누락은 별도 진단으로 구분했다.
- `testmode_control_status_s`에서 `enable`과 `mode` 두 비트필드를 발견했다. 같은 헤더의 별도 typedef와 다른 헤더를 거치는 typedef 체인이 같은 원본 정의를 가리켰다. 먼저 나온 typedef는 나중 정의에 연결됐다. 전방 선언만 있는 `Never`는 구조체 정의 미발견이다. 다른 C 범위에 있는 같은 태그의 `control.mode`는 `0~127`, 원래 범위는 `0~7`이었다.
- `device.state`는 전역 `0~3`, `func` 지역 `0~31`이었다. 헤더 원형과 C 정의를 가진 `update`에서 매개변수 `param_p`와 지역 `local_data`는 각각 `0~7`이었다. 같은 이름의 전역 포인터는 `0~3`, 다른 함수의 `local_data`는 `0~31`이었다.
- 결과 미생성 6개는 중첩 멤버 경로 4개, 확실한 일반 멤버 `wrapped.status` 1개, 카탈로그에 없는 멤버 1개다. 기존 코드는 `wrapped.status.mode`와 포인터·배열 변형을 루트 타입 조회 전의 단일 멤버 검사에서 제외했다. 진단에서는 이 행의 루트 타입까지 확인했다. 중첩 경로의 최종 멤버는 독립 정답에서 비트필드다. 파싱 실패 증거가 있거나 카탈로그에서 멤버를 찾지 못하면 비트필드 여부를 미확정으로 기록한다.
- 빈 `#define cinst`가 있는 선언과 정의가 없는 선언 모두 변수 인벤토리에 없었고, 수집기는 해당 줄에 파싱 진단을 남기지 않았다. 독립 합성 정답을 기준으로 전자는 수집 누락, 후자는 전처리되지 않은 선언으로 보고했다.
- 카탈로그 수집기가 반환하는 진단과 별도로 기존 레거시 파서의 구문 진단을 보조 증거로 기록한다. 닫히지 않은 구조체처럼 기존 카탈로그가 진단을 반환하지 않는 경우를 테스트했다. 다른 선언의 구문 오류와 멤버 누락이 함께 관측되면 `PARSE_INCOMPLETE`는 파일 수준의 불확실성을 뜻한다.

## Clang-1 독립 정답 재사용

| 대조 항목 | 기능 사례 | 스트레스 100파일 |
|---|---:|---:|
| 구조체 정의 확인 / 미확인 | 12 / 0 | 98 / 0 |
| typedef 원본 연결 확인 / 미확정 | 9 / 2 | 98 / 0 |
| 비트필드 추출 확인 / 누락 | 27 / 1 | 247 / 0 |
| 비트폭 정답 / 미확정 | 19 / 8 | 198 / 49 |
| signedness 및 범위 정답 / 미확정 | 17 / 10 | 198 / 49 |
| 변수의 원본 타입 정답 / 미확정 | 19 / 4 | 197 / 0 |

정답 건수는 구성별 번역 단위 기준이라 같은 헤더의 반복 포함을 여러 번 검사한다. 기능 데이터의 비트필드 추출 차이 1건은 이름 없는 폭 0 패딩이다. 추출과 실제 범위 수정 대상으로서의 유효성을 별개로 본다. typedef 2건은 옵션 분기 두 구성에서 `Configured` 별칭을 확정하지 못한 결과다. 변수 타입 및 확정 접근의 원본 구조체가 틀린 사례는 관측되지 않았다.

스트레스의 범위 미확정 49건은 모두 조건부 `RV_WIDTH` 매크로였다. 입력별 `-DRV_ENABLED`가 있어도 카탈로그는 전처리에 적용하지 않으므로 `BUILD_OPTIONS_PROVIDED_NOT_APPLIED`로 기록했다. 옵션 없는 조건부 선언은 별도 테스트에서 `BUILD_OPTIONS_NOT_PROVIDED`로 분리했다. 단순 `#define WIDTH 4`의 폭 계산은 가능했다. 두 헤더가 서로 다른 매크로 값을 제공하면 포함 순서를 뒤집어도 기존 분석기는 두 값을 충돌로 남겼다. `-I`를 제공해도 소스 상대 경로에서 연결되지 않은 헤더는 미연결로 관측됐다. 이러한 관측은 사내 소스에서 같은 원인이 발생한 빈도를 입증하지 않는다.

## 재현 및 개선 순서

```powershell
python -B tools/diagnose_ch1.py build/ch1-local
```

새 출력 디렉터리를 사용한다. 도구는 합성 C/H와 XLSX, 정답, 파일·구조체·변수·표현식별 JSON을 생성한다. OpenPyXL을 기본으로 사용하며 `--backend com`으로 읽기 전용 COM 검증을 선택할 수 있다. [Workbook 진단](../build/ch1-final/diagnosis.json) · [기능 정답 대조](../build/ch1-final/functional/audit.json) · [100파일 정답 대조](../build/ch1-final/stress100/audit.json)

작업 시작 회귀는 228개 중 216개 통과, 12개 건너뜀, 실패·오류 0개였다. 신규 진단 테스트 3개를 포함한 회귀는 231개 중 219개 통과, 12개 건너뜀, 실패·오류 0개였다. 건너뛴 항목은 실제 Excel 선택 회귀 11개와 바인딩이 없는 Clang AST 테스트 1개다. 위 합성 COM 읽기 검증은 전체 회귀와 별도로 실행했다. [시작 회귀 로그](../build/ch1-baseline-tests.log) · [최종 회귀 로그](../build/ch1-regression.log)

C/H-2 우선순위는 파일별 옵션과 include 가시성 및 순서의 적용, 조건부 폭 확정 근거, 컴파일러 전용 토큰의 전처리 후 선언 수집이다. C/H-3에서는 원본 타입을 따라가는 다단계 멤버 경로, 인덱스/간접 참조의 단계별 검증, 기존 판정에서 조용히 제외되던 행의 표시 정책을 다룬다.
