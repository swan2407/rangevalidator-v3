# RangeValidator Python V3.1 — 문제 분석과 수정 내용 (2026-11-04)

대상: `BMS EV SW Unit Design Specification(canfd_comm.c).xlsx` 1개를 비교했을 때
(1) 결과가 나오기까지 너무 오래 걸림, (2) 모든 행이 `확인 필요: SOURCE_CONTEXT_REVIEW … PARTIAL_READ … INPUT_CONTENT_CHANGED`,
(3) 계산 범위 칸이 비어 있음 → 계산을 못 한 것인지, 계산하고 반영을 못 한 것인지.

결론부터: **계산 자체가 시작되기 전에 세 개의 "전체 차단" 게이트에서 막혔다.** 코드의 비트필드를 읽는 단계(analysis)까지 가지 못했거나,
갔더라도 전처리 지시문 하나 때문에 파일 전체가 거부돼 범위 계산 결과가 없었다. 아래 1~3이 그 세 게이트이고, 4부터는 그 과정에서 추가로 발견한 문제다.

## 1. 느린 이유 + `PARTIAL_READ` (같은 원인)

**원인** — `com_values.py` 의 COM 읽기.
- 시트 끝을 `Cells.Find("*")` 로 찾는데, DRM 파일은 빈 문자열("")만 든 유령 칸이 시트 끝(1,048,576행)까지 있어 `"*"` 가 그 칸을 잡는다 → 범위가 100만 행으로 잡힘.
- 그 범위를 `Range.Value2` 로 **한 번에** 읽다가 메모리 부족으로 실패하면, 코드가 **셀 단위 폴백**(`ws.Cells.Item(r,c)` 를 모든 칸에 대해 호출)으로 넘어간다. 100만 행 × 열 수만큼 COM 호출 → 수십 분.
- 셀 단위 읽기에서 실패한 칸은 `cell_errors` 로 모이고, 하나라도 있으면 `result.partial=True` → 파일 상태 `PARTIAL_READ: workbook is incomplete; saving blocked` → 그 파일의 모든 행이 저장 차단.
- 병합 복원도 칸마다 `cell.MergeCells` 를 COM 으로 물어봄(최대 5만 칸).

**해결** — 상세설계서 자동화 도구에서 검증한 읽기 방식으로 교체.
- `Find("?*")`: 글자가 1개 이상인 칸만 → 유령 칸 제외.
- 값은 **행 블록 단위**(약 13만 칸/블록)로 `Value2`/`Formula` 를 읽고, 읽기 전에 `CountA` 로 빈 블록은 건너뛰며, 빈 블록이 2개 이어지면 그 뒤는 유령 범위로 보고 멈춘다. 메모리는 블록 하나로 고정.
- Find 가 실패한 쪽은 `UsedRange` 를 **상한으로만** 쓴다(행 ≤ 200,000 / 열 ≤ 256, 최소 4096행·64열은 확인).
- 병합은 범위 단위 `MergeCells` 질의로 좁혀 간다(시트 전체 → 64행 묶음 → 행 → 칸). 병합이 없는 시트는 호출 1회.
- 셀 단위 폴백 제거. 블록 읽기 자체가 실패하면 그 시트만 오류로 기록한다.
- 검증: 가짜 COM(열 Find 실패 + UsedRange 전체 + 멀리 떨어진 유령 칸)에서 openpyxl 읽기와 값·수식·병합이 100% 동일, 0.05초.

## 2. `INPUT_CONTENT_CHANGED: common #1 hash_changed=True, size_changed=False, mtime_changed=False`

**원인** — `workflow.py` 가 비교 전/후에 입력 파일의 **바이트 SHA-256** 을 비교한다. DRM 파일은 Excel 이 여는 순간 DRM 에이전트가 보호 컨테이너(접근 기록/재포장)를 다시 써서 **내용·크기·수정시각은 그대로인데 바이트 해시만 바뀐다.** 이를 "입력이 바뀌었다"로 판정해 세션 전체 저장을 차단했다(`SESSION_SAVE_BLOCKED`).

**해결** — 해시만 바뀌고 크기·수정시각이 같으면 `STABLE` (사유 `HASH_ONLY_CHANGE (DRM 컨테이너 갱신)`). 크기가 바뀌거나, 해시와 수정시각이 함께 바뀌면 그대로 `CONTENT_CHANGED`. Writer 의 "원본 변경 확인"도 크기+수정시각으로 한다. 사람이 파일을 고쳐 저장하면 반드시 수정시각이 바뀌므로 안전성은 유지된다.

## 3. `SOURCE_CONTEXT_REVIEW: contradictory/unregistered/ambiguous source` — 계산 범위가 빈 진짜 이유

**원인** — `engine.context_for()`. 설계서 시트의 머리글 위쪽에서 `.c` 로 끝나는 칸(예: 함수 정보 표의 `File | canfd_comm.c`)을 "출처 증거"로 모으고, 그 파일명이 **Common Parameter 선언의 File 열에 정확히 하나** 있어야 통과시킨다. 회사 Common Parameter 에는 `can_vcms1` 같은 전역 변수 선언 표(File/Name/Type)가 없거나, 있어도 File 이 `can_sig.h` 처럼 다른 파일이라 집합이 비어 → 오류 문자열이 만들어지고, `compare_book()` 이 **그 오류로 모든 행의 판정을 덮어쓴다**(`if context_error: status,reason,f = 'REVIEW',context_error,None`). 그래서 비트필드를 찾았든 못 찾았든 전부 같은 문구가 되고 계산 범위도 지워졌다.

같은 종류의 "전체 차단"이 두 개 더 있었다.
- `resolve()`: `catalog.reviews`(C 분석 경고)나 `common.reviews`(Common 해석 경고)가 **하나라도** 있으면 모든 행을 `REVIEW GLOBAL: …` 로 반환.
- `analysis.tokenize()`: `#include`, `#define`, `#ifdef`(3줄짜리 include guard 제외) 중 하나라도 있으면 **파일 전체를 버림**(토큰 0개). 함수 본문, enum, 중첩 구조체, `u4`·`uint8_t` 같은 typedef, 매크로 비트폭 전부 "unsupported". 실제 회사 헤더는 예외 없이 여기에 걸린다.

**해결**
- 출처(context)는 **참고 정보**로만 쓴다(Common 조회 시 같은 파일 선언을 우선할 뿐). 판정을 덮어쓰지 않는다.
- `catalog.reviews`/`common.reviews` 는 진단 정보로만 남기고 행 판정을 막지 않는다. 문제는 **그 멤버/그 선언에만** 표시된다.
- C 분석기를 새로 썼다(아래 4).

→ 질문 3에 대한 답: **"코드에서 범위를 계산하지 못한 것"** 이 맞다. 다만 계산 로직이 틀린 게 아니라, 계산 단계 앞의 게이트(출처 검사·전처리 거부·전역 차단)에서 멈춘 것이다. 반영(쓰기) 단계는 거기까지 간 적이 없다.

## 4. C 분석기 재작성 (`analysis.py`) — "typedef 사전" 아이디어 반영

제안한 방식 그대로: **1차로 소스 전체에서 typedef 를 사전으로 모으고**, 비트필드를 만날 때 그 사전으로 타입을 푼다.

- 전처리: 주석 제거, `\`+줄바꿈 이어붙이기, BOM 허용. `#define NAME 숫자/간단식` 은 **매크로 표**로 수집(비트폭 `: N_BITS`, `: (W+1)`, `: 1<<2` 계산). 나머지 지시문은 무시하고 `#if` 분기는 모두 읽는다(같은 이름이 다르게 두 번 정의되면 그 타입만 "정의 충돌" 로 표시).
- **타입 사전**: 기본형(`unsigned char` …), 관용 이름(`uint8_t`, `uint8`, `u1/u2/u4`, `s1/s2/s4`, `uint`, `boolean`, `U8` …) + 소스의 모든 스칼라 `typedef` 를 체인으로 해석(`typedef unsigned char u1; typedef u1 boolean;` → boolean = 무부호 8비트). 소스 정의가 관용 이름보다 우선.
- 구조체/공용체: typedef/태그 모두, 중첩 구조체(이름 있는 멤버는 `a.sub.b` 경로로 접근, 익명은 평탄화), `u1 a:1, b:2;` 다중 선언, 이름 없는 패딩(`uint : 4;`), 함수 포인터 멤버, 배열 멤버.
- 비트필드 범위: 무부호 → `0 ~ 2^w-1`, 부호 → `-2^(w-1) ~ 2^(w-1)-1`. 범위를 **확정하지 않는 경우**(그 멤버만 REVIEW, 사유에 적힘): `enum` 타입(GCC 무부호/MSVC 부호로 컴파일러 정의), plain `char`, 비트폭이 기본형보다 큼, 비트폭 매크로를 못 찾음, 알 수 없는 타입.
- 변수: `extern T v;`, `T v, *p, arr[N];`, `struct tag v;`, 포인터 typedef(`T_p p;`), 다른 파일에 정의된 타입(카탈로그에서 나중에 연결). 함수 정의/원형, enum 상수는 건너뛴다(enum 상수 값은 매크로 표에 넣어 비트폭 계산에 쓴다).
- 파일 단위 거부 없음. 15,600줄/구조체 600개/비트필드 12,000개 헤더 분석 0.8초.

## 5. 변수 → 구조체 연결 규칙 (`engine.resolve`)

설계서 `Name` 칸 `base.member`, `ptr->member`, `arr[i].member`, `a.sub.b` 에 대해 base 의 구조체를 이 순서로 찾는다.
1. 등록한 C 소스의 변수 선언(`extern can_vcms1_t can_vcms1;` 또는 `.c` 의 정의) — **그래서 이제 .c 파일도 등록할 수 있다**(파일 선택 창에 `.c` 추가).
2. Common Parameter 의 전역 변수 표(File/Name/Type) — 같은 파일 선언 우선, 없으면 전체.
3. 이름 규칙: `base_t`, `base_T`, `base_st`, `base_type`, 또는 base 자체가 타입 이름.
그 다음 경로를 따라 중첩 멤버를 내려가고, 마지막 멤버가 비트필드면 범위를 비교한다. 일반 멤버면 `SKIP`(대상 아님), 없는 멤버·타입 충돌·범위 미확정은 해당 행만 `REVIEW` 로 사유를 적는다.
`.`/`->` 표기 차이, 설계서 Type 빈칸, 병합된 앵커 칸은 막지 않는다(범위는 구조체가 정한다). 설계서 Type 이 코드 타입과 다르면 사유에 `설계서 Type 'u1' ≠ 코드 'uint'` 를 덧붙인다.
기존 범위 표기는 `0~1`, `0 ~ 1`, `0..1`, `0 to 1`, `[0, 1]` 을 인식한다.

## 6. Export (계산 범위 전체 반영 후 새 파일 저장) — 신규

- 기존에는 "선택한 MISMATCH 만, 전체 재비교 후, 모든 칸의 서식/도형/행높이 매니페스트를 COM 으로 다시 읽어 보존 검증" 하는 Writer 뿐이었다. 셀마다 Font/Border/Interior 를 COM 으로 읽으므로 그 자체가 또 수십 분이고, DRM 해시 게이트 때문에 실제로는 한 번도 저장까지 못 간다.
- **추가**: 비교 결과 탭의 **[계산 범위 전체 내보내기]** 버튼. 폴더 선택 창 → `선택폴더/RangeValidator_YYYYMMDD_HHMMSS/` 아래에 불일치(MISMATCH) 칸이 있는 상세설계서만 **같은 파일 이름**으로 저장(원본은 손대지 않음) + `RangeValidator_Report.xlsx`.
- Writer 동작: 원본을 Excel 로 읽기 전용으로 열고 → 대상 칸이 수식/병합 안쪽/값 변경이 아닌지 확인 → 계산 범위 기입(`=`,`+`,`-` 로 시작하면 텍스트 서식) → `SaveAs(FileFormat=51)` → 저장본을 다시 열어 기입한 칸만 확인. 서식·그림·DRM 은 Excel 의 SaveAs 가 유지한다. 전체 재비교·전체 매니페스트 제거.
- "수정 및 저장" 탭의 선택 저장도 같은 Writer 를 쓴다.

## 9. 남은 한계 / 확인 필요

- `enum` 타입 비트필드와 plain `char` 비트필드는 컴파일러 정의라 범위를 쓰지 않고 REVIEW 로 남긴다. 회사 컴파일러 규칙(예: enum 은 무부호)을 정해 주면 옵션으로 넣을 수 있다.
- `#if` 분기를 모두 읽으므로, 같은 구조체가 분기마다 다르게 정의돼 있으면 "정의 충돌" REVIEW 가 난다 → 빌드 옵션 파일을 받아 분기를 거르는 것은 다음 단계.
- 비트폭이 `sizeof(...)` 나 다른 헤더의 매크로에 의존하면 그 헤더도 함께 등록해야 계산된다(등록 안 하면 그 멤버만 "비트폭 계산 못 함").
- Common Parameter 는 선택 입력이다. 전역 변수 표(File/Name/Type)가 있을 때만 변수→타입 연결에 쓰이고, 없으면 C 소스의 선언으로 연결한다.
- Export 는 Windows + Excel 환경에서 실제 DRM 파일로 1회 확인이 필요하다(코드는 가짜 Excel 로 저장·재확인·리포트까지 검증).
