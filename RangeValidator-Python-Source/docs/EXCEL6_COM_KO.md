# Excel-6 COM 성능과 Reader 안정성

## 병합 조회 변경

기존 Reader는 시트 전체를 한 번 검사한 뒤 병합이 있는 64행 구간의 행과 셀을 순회했다. 범위 하나를 만드는 데 `Worksheet.Cells`, `Cells.Item`을 두 번씩 조회했고, 세로 병합 영역은 다음 행에서 다시 `MergeArea`를 조회했다. 병합 없는 시트는 전체 범위 검사에서 빠졌다.

`com_values._merge_state()`는 Excel이 지원하는 A1 문자열로 범위를 생성한다. `_merge_map()`은 `MergeCells`가 명시적으로 False인 사각형을 제외하고, 나머지 사각형은 행 또는 열 방향으로 나눈다. 단일 셀의 병합 여부와 `MergeArea.Address`로 앵커를 확인한다. 확인한 사각형을 시트 내부에서 재사용하고, 그 사각형에 포함되지 않는 셀은 계속 검사한다. 단일 셀 상태나 병합 주소가 불확실하면 시트 읽기 오류로 기록한다. [Worksheet.Range](https://learn.microsoft.com/en-us/office/vba/api/excel.worksheet.range) · [Range.MergeCells](https://learn.microsoft.com/en-us/office/vba/api/excel.range.mergecells) · [Range.MergeArea](https://learn.microsoft.com/en-us/office/vba/api/excel.range.mergearea)

`readers.Win32Runtime.dispatch_owned()`는 생성 전 프로세스 목록과 새 Excel의 창 PID를 대조한다. 소유권을 입증하기 전에는 Excel 설정, Open, Quit을 수행하지 않는다. Reader는 읽기 작업이 참조한 통합 문서를 `Close(SaveChanges=False)`로 닫고, 시트·통합 문서 참조를 해제한 뒤 소유한 인스턴스를 정상 종료한다.

## 동일 파일에서 변경 전후 측정

실제 Excel COM으로 각 파일을 변경 전후 각각 3회 읽었다. 시간은 중앙값이다. 호출은 병합 순회에서 관측한 `Worksheet.Cells`, `Cells.Item`, `Worksheet.Range`, `MergeCells`, `MergeArea`, `Address`의 합계이며 Excel 내부 RPC 전체는 포함하지 않는다.

| 합성 파일 | 전체 분석 전 → 후 | 병합 확인 전 → 후 | 병합 관련 호출 전 → 후 | Python 최대 작업 집합 전 → 후 | Excel 최대 작업 집합 전 → 후 |
|---|---:|---:|---:|---:|---:|
| 병합 없는 A형 | 3.609 → 3.462초 | 0.005 → 0.002초 | 6 → 2 | 47.0 → 46.3 MiB | 127.8 → 127.4 MiB |
| 병합 없는 B형 | 3.444 → 3.521초 | 0.006 → 0.001초 | 6 → 2 | 47.5 → 46.5 MiB | 127.9 → 127.7 MiB |
| 병합 적은 혼합 | 4.601 → 4.208초 | 0.480 → 0.107초 | 574 → 162 | 52.3 → 49.5 MiB | 128.4 → 127.4 MiB |
| 병합 많은 혼합 | 48.331 → 10.577초 | 44.272 → 6.370초 | 51,056 → 9,008 | 56.3 → 51.0 MiB | 129.6 → 129.2 MiB |
| 혼합 120개 | 16.597 → 10.984초 | 8.118 → 2.424초 | 9,346 → 3,442 | 82.6 → 80.5 MiB | 133.8 → 132.5 MiB |
| 혼합 200개 | 27.139 → 15.600초 | 14.528 → 3.908초 | 15,409 → 5,716 | 96.2 → 90.0 MiB | 137.0 → 136.9 MiB |
| 혼합 300개 | 36.456 → 22.060초 | 20.003 → 5.925초 | 22,999 → 8,608 | 122.7 → 112.0 MiB | 140.8 → 140.5 MiB |

300개 시트 전체 분석은 약 39.5% 줄었다. 같은 파일의 본문 읽기는 30.257초에서 16.038초로 줄었다. Open은 0.563초에서 0.536초, 시트명 조회는 0.828초에서 0.808초, Value2 단계는 0.310초에서 0.307초였다. 헤더 인식과 추출은 같은 순회에서 이루어지며 A/B 합산 중앙값은 0.178초에서 0.171초였다. 병합이 많은 파일의 `MergeArea` 조회는 1,072회에서 336회로 줄었다.

300개 시트의 전체 실행 분포는 변경 전 36.370~37.380초, 변경 후 22.032~22.134초였다. 프로세스를 매번 정상 종료했지만 운영체제 캐시와 Excel 시작 상태는 통제하지 않았다. 병합 없는 두 파일의 전체 시간 차이는 작고 B형 중앙값은 소폭 증가했다. 작업 집합은 50ms 샘플링 최고값의 중앙값이며 메모리 사용이 일관되게 개선됐다고 결론 내리기에는 3회 표본이 작다. Excel-5 보고서의 38.515초와 달리 여기서는 병합 COM 호출 계측을 켠 동일 파일의 재측정 36.456초를 비교 기준으로 썼다.

7개 파일의 모든 변경 후 실행에서 입력 SHA-256과 비교 행, 커버리지, 셀 값·수식·범위·앵커를 포함한 읽기 결과 SHA-256이 변경 전과 일치했다. 300개 시트에서 정확 추출 13,031개, 미확정 42개, 잘못된 연결·중복·예기치 않은 누락 각각 0건이었다. 세부 분포와 각 호출 수는 `performance_comparison.json`과 파일별 `*_before.json`, `*_after.json`에 있다.

## 실제 셀 예산 경계

250,000셀은 통합 문서의 채택한 함수 시트별 **관측 데이터 마지막 행 × 마지막 열**을 합산한 값이다. 서식만 있는 XFD900000은 합산에 포함하지 않았다.

| 의도한 합계 | 상태 | 결과 |
|---:|---|---|
| 249,999 | COMPLETED | 경계 표의 C2 수정 후보 유지 |
| 250,000 | COMPLETED | 정확히 한도에 닿아도 C2 수정 후보 유지 |
| 250,001 | PARTIAL | 경계 표의 A1:E4 읽기 오류를 기록하고 C2 저장 요청 거부. 뒤의 정상 시트 C2는 수정 후보 유지 |

각 파일의 경계 산술과 오류 근거는 `budget_249999.json`, `budget_250000.json`, `budget_250001.json`에 있다.

실제 열 경계 시험에서 IV열(256)은 읽혔고 IW열(257)이 있는 시트는 부분 처리됐다. 같은 파일의 정상 시트가 유지됐다. 3,100개 변수 표와 먼 서식 셀, 257열 초과 시트가 섞인 Excel-5 사례도 다시 통과했다. 기록은 `column_edge.json`과 `wide_long.json`에 있다.

별도 병합 검사 한도는 병합 가능성이 있는 시트에서 200,000셀이다. 정확히 200,000셀인 시트의 앵커·끝 값을 읽었고, 200,001셀 시트는 부분 처리하고 정상 형제 시트를 유지했다. 이 시험 호출만 통합 문서 예산을 500,000셀로 높여 두 한도를 분리했다. 긴 공란 뒤 A393217은 기본 예산에서 해당 시트가 부분 처리됐고, 시험 호출의 500,000셀 예산에서는 끝 값이 읽혔다.

두 직접 읽기 시험의 첫 실행은 부분 읽기 후 Excel 정리에 실패했다. 모의 테스트에서 시트 오류의 traceback이 Worksheet나 Range에 해당하는 참조를 종료 대기까지 보유하는 것을 재현했다. `read_workbook_values()`에서 오류 기록을 값으로 남긴 직후 예외 객체의 참조를 놓도록 수정했다. 실제 두 시험은 수정 후 각각 5.882초와 7.203초에 통과했다. 첫 실패 기록은 `*_pre_cleanup_fix.json`에 보존했다.

## Open 실패와 인스턴스 소유권

| 합성 입력 | 존재 | 시험 프로세스에서 바이트 읽기 | Open 결과 | 소유 인스턴스 통합 문서 수 전 → 후 |
|---|---|---|---|---:|
| 누락 경로 | 아니요 | 아니요 | 외부 0x80020009, 내부 0x800A03EC | 0 → 0 |
| 손상 XLSX | 예 | 예 | 외부 0x80020009, 내부 0x800A03EC | 0 → 0 |
| 배타 잠금 XLSX | 예 | 아니요 | 외부 0x80020009, 내부 0x800A03EC | 0 → 0 |
| 정상 XLSX | 예 | 예 | 완료 | 0 → 1 |

실패 단계는 모두 `com.Workbooks.Open`이었다. 세 실패 뒤 정상 파일을 처리했고, 정상 파일만 정확한 파일명으로 `Close(SaveChanges=False)`를 호출했다. Excel 인스턴스 네 개의 소유권을 확인했고 모두 정상 종료됐다. 개발용 `open_audit.json`에 합성 파일명, 존재·접근성, Open 인수, 예외 메시지와 EXCEPINFO, PID, 문서 수, Close 대상과 정리 결과를 기록했다. 배포 진단의 경로·내용 마스킹은 유지된다. 세 재현 조건이 같은 HRESULT를 반환했으므로 회사 파일의 실패 원인은 이 코드만으로 식별할 수 없다.

별도 STA의 감시용 Excel에 합성 문서를 열고 Reader와 Writer를 실행했다. 감시 인스턴스와 작업 인스턴스의 PID가 달랐고, 열린 문서의 창·이름·개수·값·저장 상태가 유지됐다. 시험이 소유한 프로세스만 정상 종료했다. 모의 테스트는 기존 PID를 받으면 Excel 설정, Open, Quit 전에 차단되는 것도 검사한다. 실제 사용자가 열어 둔 파일, 동일 STA 감시의 Excel-5 연결 해제 재현, 회사 DRM·ACL 환경은 이번 시험 범위 밖이다.

## 파일 수에 따른 Writer 비용

각 조합의 수정 대상은 1,000셀로 고정하고 파일에 균등 배분했다. 원래 값, 기대값, 주소, 저장 후 실제 값, 수식 여부를 독립 COM 재열기로 대조했다. 모든 셀이 `SAVED_VERIFIED`였고 원본 SHA-256은 같았다.

| 파일 수 | 입력 바이트 합계 | SaveAs | Writer 재열기 | Writer 검증·정리 | Writer 전체 | 추가 COM 재열기·대조 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 21,138 | 0.042초 | 1.045초 | 7.198초 | 24.606초 | 3.435초 |
| 2 | 33,299 | 0.096초 | 1.927초 | 9.481초 | 30.504초 | 6.819초 |
| 5 | 58,352 | 0.229초 | 5.170초 | 16.513초 | 51.439초 | 17.553초 |
| 10 | 101,145 | 0.449초 | 9.645초 | 27.657초 | 84.462초 | 33.991초 |

Writer 재열기는 파일별 COM 기동과 Open을 포함한다. 추가 COM 대조는 기존 Writer 검증이 끝난 후 독립 실행한 시험으로 Writer 전체 시간과 분리했다. 파일별 고정 구조와 압축 오버헤드 때문에 파일 총 크기는 같지 않다. 각 조합은 실제 COM에서 1회 실행했으므로 실행 시간 분포는 Reader 벤치마크에만 있다. `write_1.json`, `write_2.json`, `write_5.json`, `write_10.json`과 각 하위 `cells.json`에 결과를 기록했다.

실제 Writer 정책 시험에서 AUTO_MISMATCH, AUTO_CREATE, MANUAL_REVIEW가 각각 `SAVED_VERIFIED`였다. 수식과 병합 비앵커 셀은 수동 수정 요청에도 `SKIPPED`였고 미확정 두 셀에는 수정 후보가 없었다. 공유 잠금이 걸린 파일은 `writer.lock`에서 Win32 코드 32로 `SAVE_FAILED`가 됐으며 정상 파일의 `_fixed.xlsx`는 저장·재열기 검증됐다. 실제 COM으로 보고서의 Summary, Mismatch, Review, Errors, Results 다섯 시트를 확인했다. 두 원본 해시는 유지됐다. 세부 결과는 `writer_policy.json`에 있다.

## 정확성 및 회귀

- 실제 COM 기준선은 정답 7,793개 중 7,788개 정확 추출, 미확정 5개, 잘못된 연결 0건이었다. A형 3,853개, B형 3,935개, 기존 혼합 120개 시트 7,260개가 일치했다. A형 105개 시트 주소 15,981쌍과 B형 100개 시트 변수 18,075개를 다시 대조했다. 기록은 `baseline.json`과 `b100.json`에 있다.
- 새 모의 COM 테스트 4개는 사각형 경계를 가로지르는 병합, 병합 없는 시트와 단일 셀 불확실, 기존 PID 차단, 부분 읽기 참조 해제를 확인했다. 기존 COM 테스트 더블은 Excel의 A1 문자열 Range 입력을 지원하도록 확장했으며 기존 기대값은 유지했다. 참조 해제 수정 뒤 관련 모의 테스트 14개가 통과했다.
- Windows Tk 선택 테스트 5개를 활성화한 전체 회귀에서 224개를 실행해 213개가 통과했다. 실제 Excel 선택 테스트 11개를 건너뛰었으며 실패·오류는 없었다. 실제 Excel은 위의 별도 검증으로 실행했다. Tk 창 종료 때 `ttk::ThemeChanged` 경고가 출력됐지만 GUI 테스트는 통과했다.

## 실행과 남은 확인 항목

Windows Python과 pywin32로 `tools/excel6_benchmark.py`를 실행한다. 결과 디렉터리 인수 뒤에 `before` 또는 `after`를 넘기며 기본 반복 횟수는 3이다. 이번 `before`는 Reader를 수정하기 전 실행했고, 당시 Git 상태·diff와 Reader 사본을 결과 디렉터리의 `baseline`에 보존했다. 동일 합성 파일을 사용해 `after`를 실행한다. 경계·오류·Writer 검증은 `tools/diagnose_excel6.py`에 결과 디렉터리와 `reader` 또는 `writer`를 전달해 실행하며, `--case`로 개별 사례를 실행할 수 있다.

병합이 없는 파일의 성능은 COM 기동 편차와 함께 추가 측정할 여지가 있다. Writer는 파일마다 열기와 검증을 수행하므로 같은 총 수정 셀 수에서도 파일 수를 따로 기록한다. 이후 C/H 분석을 검증할 때는 현재 확정한 Excel 좌표·원본 값·수정 가능 여부를 독립 정답으로 유지하고, 이름 중복·구조체 멤버 모호성·타입 불일치에 대한 결과를 별도로 비교한다.
